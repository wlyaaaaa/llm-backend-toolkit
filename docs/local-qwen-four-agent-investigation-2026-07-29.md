## 为什么先前会显示 4/30

发现两项独立设施问题：

1. 通用评测脚本允许在缺少 `LLM_TOOLKIT_AICLI_ENTRY` 时继续创建任务目录。12 项任务随后都在 19–106 毫秒内失败，错误为 `LLM_TOOLKIT_AICLI_ENTRY is not configured`，实际模型调用数为零。脚本现要求 `--aicli-entry` 或环境变量，并在创建输出目录前失败关闭。
2. AICLI 外层 Windows 沙箱曾按修改时间选中较新的 Desktop `codex.exe`，但该目录没有匹配的 `codex-windows-sandbox-setup.exe`；npm Codex 0.145.0 自身包含完整配套资源。Claude Code、Qwen Code、OpenCode 因共同外层沙箱未启动而被误记最低分。AICLI 现固定从同一 npm 包解析启动器与 helper，缺少唯一匹配资源时拒绝运行。修复后，三套 CLI 连接本地模型的 `PONG` smoke 均 exit 0。

这两类 4/30 均是 harness/启动链证据，不是模型能力证据。

## 旧 30/30 与本轮 28/30 的直接解释

两次 Codex 运行使用相同 suite fingerprint、相同模型 digest、相同 Codex CLI 0.145.0 和同一当前源码入口，可以直接比较：

- 旧最终运行完整列出全部未选任务，得到 30/30。
- 本轮选择、顺序、总时长和总价值均正确，但 `skipped` 漏了 `H`，得到 8/10。
- 任务正文已明确要求每个未选任务出现一次；本轮模型仍漏项，属于生成与工具检查后的单次完成度波动。
- 公开 `check.py` 有意只做结构检查，隐藏 verifier 才做最优性、完整性和理由检查。模型运行公开检查得到 `STRUCTURE_OK` 后没有自行做第二遍语义枚举。

因此，旧 30/30 不是伪造，本轮 28/30 也不是本地模型能力崩坏。更准确的表述是：该组合的已观测最好结果为 30/30，但单次稳定结果并非锁定 30/30。若要衡量成功概率，需要预先定义多样本可靠性协议；本轮遵守“不多次复测”，不靠重复抽样挑高分。

## 更新兼容的稳定方案

唯一办法不是停止更新 CLI。稳定方案应把“发现更新”和“替换受管运行时”分开：

1. 活跃槽保留 last-known-good 的完整版本目录，不原地覆盖。
2. 新版本进入候选槽，CLI、原生可执行文件、helper 和资源目录作为一个不可拆分闭包。
3. 晋升前先做不调用模型的版本/资源/协议探测，再做少量本地 smoke；版本变化同时使旧验收指纹失效。
4. 只有资源闭包、沙箱、必要协议字段、硬限制和清理都通过才原子切换活跃槽。
5. 候选失败不自动 fallback 到另一个模型，只继续使用上一活跃槽并保留失败回执。

本轮已经实现第 2 项在 Codex sandbox 解析处的原子绑定和失败关闭；四套 CLI 通用的自动候选槽安装器尚未实现。因此当时可以继续更新，但更新后必须重新验收，不能把 npm/桌面端中“修改时间最新”的零件混装为生产运行时。
